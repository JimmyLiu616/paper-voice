# 照片等待時間：提前載入模型

2026-10-02。本輪依新目標優先處理照片速度與在地語言朗讀，未繼續部署先前的地點候選。

工作台開啟後，若本機模型已安裝，會以空白請求提前載入同一個 Gemma 3；選取照片時也會嘗試準備。使用者可以同時選圖或拍照，畫面顯示準備狀態。讀圖、OCR、欄位擷取、引文檢查及問答內容均未改動。

## 真實圖片 API 配對

| 原創虛構範例 | 未預載：上傳到結果 | 預載完成：上傳到結果 | 提前準備耗時 |
|---|---:|---:|---:|
| 補件通知 | 28.919 秒 | 8.295 秒 | 20.462 秒 |
| 社區活動 | 25.454 秒 | 7.485 秒 | 19.072 秒 |

兩組的辨識全文、七個欄位皆完全相同。測試使用同一張圖片和同一條真實 OCR／Gemma／API 路徑，每次先卸載 Gemma，第二張圖倒轉比較順序。每個條件只有一次觀察，未清空作業系統檔案快取，不能當作一般效能保證。

這是把模型載入移到選圖前，**不是模型推論變快，也不是省掉準備時間**。如果開頁後立即上傳，仍可能等模型載入；計入準備時間後，總計算時間沒有相應縮短。既有預熱狀態下的日常速度、長公文和不同硬體需要另外評估。

預載不傳文件、不下載模型；處理文件時不另排預載工作。相同頁面的同時準備請求會合併，成功後一分鐘內選圖不重送。健康檢查的定時輪詢不會重複預載，因此仍沿用五分鐘閒置卸載；準備失敗不阻止直接上傳。

## 沒有採用的捷徑

- 簡化為每欄只生成一段文字：五份已保存的公文開發逐字稿，原版欄位檢查 20/20，候選 15/20。生成較少，但錯把附件當應備文件、漏費用與限制，因此未採用。
- 直接從已保存的 Windows OCR 初讀文字整理：19/20，最後一頁期限未通過。沒有改成預設，也沒有把這個文字實驗當成照片端到端測速。

完整計數、每次生成 token／載入時間和檔案雜湊见 [decision.json](decision.json)；照片配對見 [summary.json](summary.json)、[photo-runs.json](photo-runs.json)。第一個簡化試驗的基準含冷載入，故不能把該組全部時間差歸因於縮短輸出。

Python 189 項、JavaScript 25 項通過。另以 AST 比較確認七個文件處理函式未改動。沒有新微調或保留測試推論，沒有把不可靠的捷徑部署到正式服務。
