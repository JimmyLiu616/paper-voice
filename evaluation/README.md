# 可重現的文件評測

這是新建的原創合成測試，不是目標族群研究，也不是一般 OCR 準確率基準。8 個開發文件模板、4 個保留模板，每份各有清晰版与傾斜 2.3 度加模糊／壓縮版。同一份文件的所有變體留在相同分組；變體不視為獨立文件。

`cases.json` 包含本專案建立的檢查條件與問題，尚未由獨立人員複核；`manifest.json` 記錄來源與圖片 SHA256。所有單位、活動、地點均為虛構，採 MIT。影像由 Pillow 與 Windows 微軟正黑體產生；此專案不散布字型檔。完整標註文字與影像對應，沒有把受測模型的辨識輸出當標準答案。

```powershell
.\.venv\Scripts\python.exe scripts\build_eval.py
.\.venv\Scripts\python.exe -X utf8 scripts\evaluate_documents.py --name baseline-v1
.\.venv\Scripts\python.exe -X utf8 scripts\evaluate_documents.py --name candidate-v2
# 只用標準文字，隔離 OCR 與下游理解錯誤：
.\.venv\Scripts\python.exe -X utf8 scripts\evaluate_documents.py --name candidate-text-v2 --text-only
```

執行前啟動本機服務。已有 run 不會覆寫；中斷可加 `--resume`，但程式、資料與模式雜湊必須相同。逐筆寫入 `runs/<name>/results.jsonl`，最後產生 `summary.json`。若程式或資料變更，使用新 run 名稱。

从 candidate-v4 開始，同時保存 app.py、corpus.py 與評測程式原始碼快照。較早紀錄只有程式雜湊與輸出，沒有完整歷史原始碼，不可宣稱能精確重建早期版本。評測前需確保服務已重啟並載入對應程式；雜湊來自磁碟檔案，不是伺服器版本遠端認證。

後續已在 `/api/health` 增加服務啟動時固定的 `app_sha256`；目前評測程式會先與磁碟原始碼比對，不同或缺少即停止，必須先重啟服務。`candidate-v6` 因啟動版本歸屬不正確已標 `INVALID.md`，不納入比較；保留部分記錄作為稽核痕跡。

## 指標如何解讀

- OCR CER：NFKC、移除空白、保留標點，相對於合成文件標準文字的字元編輯距離。模型把字詞讀錯、漏字或改標點都計入。
- 欄位檢查：檢查必備片段、應留空欄位及禁止混入的日期／金額。移除標點與空白後比對，**不是完整語意正確率**；額外錯字或無關內容仍可能通過。
- 問答檢查：檢查是否回答／拒答及指定答案片段。標記 `found=true` 且 `contains=[]` 的題目僅測可回答性，必須人工讀答案判斷正確，不可稱為已答對。
- 沒有明示資訊的欄位設計為留空。「未設定截止日」這種安全文字也可能因格式規範未留空而計為失敗，不能將全部失敗都描述成危險錯誤。
- 清晰與模糊兩版不是兩個獨立樣本。時間受暖機、Ollama 快取與其他程序影響，不是嚴格速度實驗。
- 同時報告錯誤案例數，不能只報成功案例的通過比例。

## 分組與迭代

`dev` 用來找問題與調整；`test` 留待候選版本及評估規則凍結後，使用 `--split test --final-evaluation` 才執行。來源資料可見並不代表盲測，因此只能稱為「未用於本輪調參的保留測試」，不能稱外部獨立認證。

目前執行 test 還需提供 `--freeze evaluation/freeze-candidate-v9.json`，核對凍結的程式、OCR、評測器、資料雜湊及模型 digest。這份凍結紀錄屬於 v9；修改凍結檔案後應另存新的候選紀錄，不能覆蓋舊紀錄來規避檢查。新評測摘要另外保留 planned 分母及 complete 狀態，避免中途失敗縮小分母。

微調資料應另建 train split；不得把本輪 dev/test 的錯誤案例直接塞進訓練集後再用同一組宣稱泛化改善。需要以文件來源／模板家族切分，同源照片、裁切與模糊增強必須一起分組。

## v9 首次保留測試與文字對照（2026-10-01）

在首次執行前保存 `freeze-candidate-v9.json`，預先指定圖片與標準文字兩種測試；兩者之間沒有修改模型、提示詞或程式。4個保留文件家族，圖片共8張。實際執行記錄為 `runs/holdout-v1/` 和 `runs/holdout-text-v1/`。

| 輸入 | 欄位檢查 | 四類重點檢查 | 問答檢查 | 執行錯誤 |
|---|---:|---:|---:|---:|
| 8張圖片 | 35/42 | 19/24 | 12/16 | 0 |
| 4份標準文字 | 19/21 | 11/12 | 7/8 | 0 |

各分母不同，圖片有同源變體，不將兩列合併成準確率。圖片總編輯距離13／標準文字字元1316（NFKC、去空白、保留標點），但字元錯誤少不代表答案正確。底層 CER 函式的 `scope` 固定文字含 human-corrected；此處的參考文字實際是專案原創合成稿，並非獨立人工校對。

主要發現：

- 學校回條清晰圖漏掉同意書與緊急聯絡表的部分字；模糊版及標準文字通過，不能推論模糊一般更好。
- 停水通知即使輸入正確標準文字，仍回答甲乙棟「會停電」，並引用只談停水的段落。引用存在沒有保證回答得到支持。圖片版另漏掉「丙棟不受影響」的回答。
- 模型把儲水行動加入自行編寫的「備註」再串接其他段落，逐字匹配因此隱藏行動卡。這是模型未遵守擷取格式及後處理恢復能力不足，不能直接關閉引用檢查。
- 預約變更的模型原始截止日是正確的11月30日，程式擴張上下文後混入12月13日。這項失敗由程式造成，微調不能替代修正段落邊界。
- 「取消不收手續費」「本次作業不向住戶收費」未填入費用卡；原檢查沒有覆蓋這兩项，不能因通過片段檢查就稱完整擷取。
- 英文 photo ID 被譯成不自然的「照片身份證」；代領問題標為拒答，但原文有 in person，至少可以告知本人領取要求。此題的標註及判準仍待複核，12/16不是經人工認證的正確率。

原始模型擷取／驗證後欄位的診斷紀錄見 `diagnostics/heldout-v1/`；這是另一次真實推論，與原評測分開，不回填或重算原始分數。標準文字仍出現主題混淆，足以把「文字理解／拒答能力」列入微調候選。該次診斷時尚未建立 CUDA 訓練環境或原生 checkpoint；後續已完成獨立合成單批 QLoRA 可行性實驗，見 `training/LORA_SMOKE.md`，仍沒有人工複核的任務訓練集或任務品質改善證據。

這四個家族已開啟並用於診斷。v9首次凍結結果保留；之後依這些錯誤修改的版本，對同一組只能稱回歸，需另備新來源才能再宣稱保留測試。

## 語意核對器開發實驗

另見 `qa-completeness/deadline-prompt-v1/` 的問答完整性提示實驗：21題成對比較與3題追加診斷，使用相同真實擷取結果，包含逐例答案、引文、機械檢查與 Codex 審閱。候選從19/21提升至20/21，卻新增無關引文，因此未部署。測試腳本為 `scripts/experiment_complete_deadlines.py --name <new-run-name>`；報告內 runner 檔案是當次程式快照，其路徑以原執行位置為準。不得將機械片段分數當成完整語意正確率，也不能把標準文字結果當成示範影片 OCR 問題已修復。

`answer-verification/cases.json` 是17筆已在推論前由 Codex 編寫的開發題，包含8組正反例及1筆已知的停水／停電錯誤。這是對預先編寫候選答案的判別測試，不是完整上傳→問答流程，也未經獨立人工標註審核。
