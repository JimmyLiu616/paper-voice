## 已取得的依據

v9 已完成首次凍結保留測試：4個家族8張圖，欄位35/42、問答12/16；相同4份標準文字為19/21、7/8。最重要的新證據是「停水」文件在標準文字輸入下仍回答「停電」，因此不再僅將殘留問題歸於 OCR。模型原始輸出診斷另發現行動欄自行串接備註；而截止欄混入另一個日期則由程式擴張段落造成。詳見 `../evaluation/README.md` 與 `../evaluation/diagnostics/heldout-v1/`。這些案例不可直接轉成 train 後仍當 test。

下一階段將工作分開：先修段落邊界造成的截止欄污染；對「答案換了事件／對象但引用仍存在」建立不同來源、不同模板的正反例，測試能否透過提示／回答驗證改善。若這類標準文字錯誤在新的開發樣本仍反覆發生，文字理解 LoRA 有明確的實驗目標。候選資料需包括有答案、相似但不同主題、否定、例外與真正未提及，不能只蒐集會回答的正例。訓練成果比較必須包含錯誤自信回答，不能只比較格式通過率或 loss。

已追加17筆語意核對開發題：8組正反例及1筆已知錯誤，涵蓋服務主題、對象、收費、期限、英文與否定／資格；候選答案由專案編寫，不是主模型實際產生的17個答案。Gemma 的兩版核對提示都保留8/8正確答案，但只拒絕6/9錯誤答案；Mistral Ministral 3 3B 的英文提示為6/8、6/9且4次輸出截斷，中文提示為5/8、8/9。各版本均未接入正式流程。判定標籤通過也可能伴隨錯誤或自相矛盾的理由，不能當成獨立人工語意審核。完整輸出在 `../evaluation/answer-verification/runs/`。

這些失敗支持繼續準備語意判別／引用忠實性的訓練候選，但17筆開發題不足以作訓練成效證據，且已加入訓練資料排除檢查。語意核對階段的 Mistral 使用 Ollama GGUF；後續已另下載 Apache-2.0 原生 BF16 checkpoint 並建立 CUDA 環境，完成單批 QLoRA 可行性實驗。來源見 `MODEL_SOURCES.json` 的 experimental_models；未變更核心服務模型，任務微調仍需經複核的不同來源資料。

正式流程目前採用可驗證的日期段落修正及有限服務主題一致性檢查：只有引用明說某項服務，而單一問題／答案換成另一項時拒答；不推論未提及的服務狀態，也不宣稱能驗證所有否定、金額或資格。這些是程式優化，不是模型權重訓練。

新增4份網路官方 PDF、5頁原版公文測試後，v5 的欄位檢查僅5/20。新錯誤包含附件／應備文件混淆、跨行資料被隱藏、差別費率漏條件，以及雙欄小字轉寫省略收費關係。這否定了「合成文字全通過即可推論理解沒問題」的外推。先修正輸出驗證與段落保留，再以公文完整標準文字隔離剩餘理解錯誤；這批公開文件已成為開發集，不可再用作微調泛化證據。歷次公文結果见 `evaluation/public-documents/`，仍未訓練模型權重。

第一輪 `evaluation/runs/baseline-v1`：16 張合成圖（8 個文件家族、各兩種影像條件），欄位片段／留空檢查 82/102，問答檢查 28/32。這些不是一般準確率，詳見 evaluation/README.md。實際錯誤包括取消活動日期當截止日、漏掉郵戳條件、應備文件漏字。先修復語意欄位與引用保留，再分離殘留 OCR 與理解錯誤。

### 原文片段格式試驗（未採用）

`span-fields-v1` 以5份既有公文OCR轉寫及8份合成標準文字，比較應備文件／例外條件兩欄。簡化為兩個原文片段字串、由程式用同一片段建立 evidence，沒有改善既有20項檢查：原流程18/20，候選16/20，13次執行皆完成，但原始模型輸出有10個不符合逐字來源的片段。這個20項分母只含兩欄，與 public-v8 的5頁四欄18/20不是同一基準。

兩個原本正確留空的案例退步：報名方式和電梯維修段落被當應備文件。補助頁的候選也把資格當文件，即使選取的字串確實在原文裡仍是語意錯誤。正式流程維持v12；完整輸出保存在 `.runtime/span-fields/span-fields-v1/`，可公開摘要與人工代理檢視見 `evaluation/public-documents/span-fields-v1-summary.json`、`span-fields-v1-review.json`。

這支持後續標註需同時覆蓋類別判斷與逐字忠實性，不能只把 evidence 省略或只教模型複製字串。12份乾淨合成通知草稿還不足以代表真實OCR噪音；可追加經授權、人工核對的斷行／錯字文本對照與「未提及就留空」反例。既有失敗題留在開發集，不能直接挪入訓練再宣稱泛化。實驗沒有證明微調必然有效。

1. **文件理解 LoRA**：針對標準文字仍反覆漏條件、混淆事件或填錯欄位建立任務資料。目前實作及CUDA驗證使用原生 Ministral 3 3B BF16 checkpoint 配合NF4／LoRA，見 `DOCUMENT_LORA.md`；它不是正式Gemma的微調權重。較早考慮的Gemma QLoRA仍屬未實作方向。即使Ministral任務adapter訓練成功，也要與原Ministral及目前Gemma在相同資料、推論條件下分別比較，不能因adapter可載入就替換正式模型。不能直接把Ollama GGUF當Transformers訓練權重。
2. **VLM OCR LoRA**：若標準文字流程正確，主要錯誤出在圖片轉文字，建立有來源授權、人工核對的圖文對，針對視覺／語言適配器做小規模實驗。現有純文字修正匯出不含影像，因此不足以訓練 VLM OCR。合成文件可驗證訓練流程，但不能代表真人拍照泛化。
3. **指定 ASR LoRA**：使用 `adi-gov-tw/Taiwan-Tongues-ASR-CE-pretrained-v1.0` 原生 Transformers 權重；現有 `Taiwan-Tongues-ASR-CE-v1.0` 是推論格式。需要真人錄音與人工逐字稿，以說話者分組，不把同一位說話者或同句合成音頻放進 train 和 test。兩句 TTS 只足以測串接，不能支持在地語音微調成效。

先依文件基準決定 1 或 2，避免沒有語音資料就先訓練 ASR。既有服務環境與訓練環境分開，保留原模型回退；下載權重前確認磁碟空間與授權取得方式，不自動變更帳號同意狀態。

## 實验規範

- 第一個訓練批次之前，固定訓練／開發／測試來源、模板家族與隨機種子。資料列記錄 `source_id`、`family`、`split`、`license`、`rights_confirmed`、`human_reviewed`，不自動使用私人上傳照片或錄音。
- 純合成 smoke run 可以證明 optimizer／adapter 可以更新；訓練 loss 下降不代表任務改善。不得把 smoke run 描述成已完成有效微調。
- 原模型與 adapter 使用相同評測圖片、提示詞、量化條件與後處理；如果後處理同時變更，另外做消融比較。
- 先在 dev 決定 adapter 與推論設定，再執行保留 test。若看過 test 後繼續调參，该 test 即降級成 dev，另建新保留來源。
- 上線條件：關鍵日期／金額不新增錯填、否定與例外條件不退步、主要任務指標優於基準、記錄速度與顯存。小樣本只報逐例結果，不宣稱統計顯著或普遍優越。
- 不通過就保留原模型，記錄失敗實驗與原因。成功 adapter 需附基礎模型名稱／revision、adapter 配置、訓練步數、資料卡、權重與依賴授權、比較結果。
